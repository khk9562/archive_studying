> 📅 **학습일**: 2026-08-28

> 🧭 데이터센터 인프라 모니터링(프로젝트S)을 이해하기 위한 **최소한의 네트워크 기초**. 네트워크 정규 강의(CCNA 등)까지 갈 필요 없이, "데이터센터에 뭐가 꽂혀 있고 서로 어떻게 연결되나" 그림 하나만 잡으면 된다.


## 0. 큰 그림 — 사무실 건물 비유


데이터센터를 큰 사무실 건물이라고 치면:

- **서버** = 일하는 사람 (실제 계산·서비스를 함)
- **스토리지** = 창고 (데이터를 보관함)
- **스위치** = 복도·엘리베이터 (사람과 창고 사이를 오가는 통로)

제품명 프로젝트S 의 SNS 가 정확히 이 셋(Server, Network, Storage)이다.


---


## 1. 망(網)과 대역


**망(network)** = "서로 직접 대화할 수 있는 컴퓨터들의 묶음". 건물로 치면 **한 층**. 같은 층 사람끼리는 그냥 걸어가 말을 걸 수 있고, 다른 층에 가려면 엘리베이터(라우터)를 타야 한다.


**IP 주소** = 그 안에서의 자리 번호.


```plain text
10 . 10 . 20 . 5
└──────┬─────┘ └┬┘
   어느 층인가   그 층 몇 번 자리인가
```

- `<ip주소>` 와 `<ip주소>` → **같은 층**. 서로 바로 통신됨
- `<ip주소>` 와 `<ip주소>` → **다른 층**. 엘리베이터 없으면 못 감

**대역(帶域)** = 그 "층 전체"를 가리키는 말. `10.10.20.x` 대역, `10.10.99.x` 대역. 정확한 용어로는 **서브넷(subnet)**.


> 💡 "대역이 다르다" = **층이 달라서, 엘리베이터(라우팅)를 뚫어주지 않으면 모니터링 서버가 그 장비에 도달할 수 없다**는 뜻.


**게이트웨이(gateway)** = 그 층의 엘리베이터 위치. 다른 층으로 나갈 때 무조건 여기를 거친다. 그래서 장비에 IP 를 줄 때 IP·서브넷·게이트웨이를 항상 세트로 적는다.


**VLAN** = 물리적으로는 같은 층인데 **가벽을 세워 논리적으로 나눈 것**. 케이블을 새로 깔지 않고 설정만으로 "이 포트들은 A 구역, 저 포트들은 B 구역" 선을 긋는다. 대역과 VLAN 은 보통 1:1 로 짝지어 쓴다 (VLAN 99 = 10.10.99.x 대역).


---


## 2. NIC — 랜카드


**NIC (Network Interface Card)** = 랜 포트, 랜카드. 노트북에 랜선 꽂는 그 구멍이 NIC 하나다.


핵심은 **서버는 NIC 를 여러 개 가진다**는 것. 서버 뒤판에는 랜 포트가 4개, 8개씩 달려 있고 **NIC 마다 IP 를 따로 준다.**


| NIC    | 연결되는 망 | IP 예시      | 용도              |
| ------ | ------ | ---------- | --------------- |
| NIC 1  | 서비스망   | <ip주소> | 실제 서비스 트래픽      |
| NIC 2  | 백업망    | <ip주소> | 야간 백업 (무거워서 분리) |
| BMC 포트 | 관리망    | <ip주소> | 아래 3번 참조        |


> ⚠️ "서버 한 대 = IP 한 개"가 아니라 **"랜 포트 한 개 = IP 한 개"**. 그래서 서버 목록에 IP 가 여러 개 보인다.


---


## 3. BMC / iLO — 서버 안에 든 또 하나의 작은 컴퓨터


서버 메인보드에는 **본체와 별개로 돌아가는 아주 작은 관리용 컴퓨터**가 박혀 있다. 이것이 **BMC (Baseboard Management Controller)**.


결정적 특징: **서버 본체가 꺼져 있어도, OS 가 죽어 있어도 BMC 는 살아 있다.** 전원 케이블만 꽂혀 있으면 동작한다.


BMC 로 하는 일:

- **원격 전원 켜기/끄기/리부팅** (데이터센터에 사람이 안 가도 됨)
- **하드웨어 상태 읽기**: CPU 온도, 팬 RPM, 파워서플라이 고장, 메모리 오류
- **원격 화면 접속**: 모니터·키보드를 꽂은 것처럼 부팅 화면부터 보임

BMC 도 자기 전용 랜 포트를 가지고 IP 를 따로 받는다. **iLO / iDRAC 은 제조사별 브랜드명**일 뿐 같은 것이다.


| 이름             | 정체                                              |
| -------------- | ----------------------------------------------- |
| BMC            | 일반 명칭                                           |
| iLO            | HPE 서버의 BMC                                     |
| iDRAC          | Dell 서버의 BMC                                    |
| IPMI / Redfish | BMC 와 대화하는 통신 규약 (IPMI 구형, Redfish 신형 REST API) |


> 💡 서버가 다운돼 OS 응답이 없어도 온도·전원 상태를 보여줄 수 있는 이유 = 그 데이터가 OS 가 아니라 **BMC** 에서 오기 때문.

## 4. iSCSI / NFS / FC — 서버가 창고(스토리지)를 쓰는 방법


진짜 데이터는 외부 스토리지 장비에 둔다. **그 창고를 어떻게 갖다 쓰느냐**가 이 용어들이다. 먼저 두 방식:


**① 블록(block) 방식** — 스토리지가 **"빈 디스크 한 덩어리"** 를 통째로 넘겨준다. 서버 입장에서는 새 하드디스크를 꽂은 것과 똑같아 보여서 직접 포맷하고 파일시스템을 만든다. 빠르고 DB 처럼 성능이 중요한 데 쓴다.


**② 파일(file) 방식** — 스토리지가 **이미 만들어진 공유 폴더**를 열어준다. 윈도우 네트워크 드라이브와 같은 감각. 여러 서버가 동시에 같은 폴더를 본다.


| 용어                 | 방식 | 어떤 선으로 가나         | 비유             |
| ------------------ | -- | ----------------- | -------------- |
| FC (Fibre Channel) | 블록 | 전용 광케이블 + SAN 스위치 | 창고 전용 고속 전용도로  |
| iSCSI              | 블록 | 일반 랜선(이더넷)        | 같은 일을 일반 도로로   |
| NFS                | 파일 | 일반 랜선             | 공유 폴더 (리눅스 계열) |
| SMB/CIFS           | 파일 | 일반 랜선             | 공유 폴더 (윈도우 계열) |

- **FC** 는 빠르고 안정적이지만 전용 장비(HBA 카드, SAN 스위치, 광케이블)가 다 따로 필요해 비싸다. **SAN 스위치**가 이 전용 도로의 교차로
- **iSCSI** 는 "FC 와 같은 블록 방식을 전용 장비 없이 랜선으로 하자"는 것. 그래서 IP 가 필요하고 스토리지망을 따로 뺀다
- **NAS** = 파일 방식(NFS/SMB)으로 서비스하는 스토리지 장비. 반대로 **SAN** = 블록 방식 스토리지 네트워크

## 5. SAN 스위치에 IP 가 없으면 왜 문제인가


> 🚨 SAN 스위치는 **IP 를 안 줘도 동작은 하지만, 그러면 모니터링이 아예 불가능한** 대표적인 장비다.

- SAN 스위치의 **데이터 평면은 FC** 라서 IP 가 없다. 서버 HBA ↔ 스위치 ↔ 스토리지는 **WWN**(포트 고유 주소)으로 통신하고 TCP/IP 스택을 타지 않는다. 즉 **실어나르는 트래픽에는 IP 가 필요 없다**
- 문제는 **관리·조회**할 때다. SAN 스위치에는 별도의 **이더넷 관리 포트**가 있고 여기에 IP 를 줘야만 SSH CLI(`switchshow`, `porterrshow`, zoning), SNMP 폴링, REST API(Brocade FOS RESTConf 등)가 열린다
- IP 가 없으면 남는 접근 수단은 **시리얼 콘솔 케이블뿐** → 원격 모니터링 원천 불가
- 프로젝트S 도 `san_switch` 를 장치로 등록해 메트릭 서버가 SNMP/SSH 로 폴링하는 구조라(`docs/domain/data-sources.md`), 관리 IP 가 없으면 **장치 등록 단계부터 막힌다**

### 설계 문서 받았을 때 확인할 항목

- [ ] SAN 스위치 **관리 포트 IP / 서브넷 / 게이트웨이** 가 IP 할당표에 있는가
- [ ] SAN 스위치는 보통 **A/B 패브릭 이중화로 2대 이상** — **대수만큼** IP 가 잡혀 있는가 (실무에서 자주 빠지는 항목)
- [ ] 블레이드 섀시 내장형이면 관리 경로가 섀시 관리모듈(CMC/OA)인지
- [ ] 모니터링 서버가 **어느 대역에 놓이고**, 관리망까지 라우팅 경로가 있는가
- [ ] 방화벽/ACL 이 있으면 **UDP 161(SNMP), TCP 22(SSH), TCP 443(REST)** 이 열려 있는가
- [ ] SNMP community / v3 계정, SSH 관리자 계정 발급 계획이 있는가

## 6. 왜 굳이 망을 다 나누나

1. **보안** — 관리망(BMC·스위치 관리 포트)은 뚫리면 서버 전원까지 조작당한다. 서비스망과 절대 안 섞는다
2. **성능** — 백업·스토리지 트래픽은 덩치가 커서 서비스 트래픽과 같은 길을 쓰면 서로 방해한다
3. **장애 격리** — 한 층의 사고(브로드캐스트 폭주 등)가 건물 전체로 번지지 않게 한다

## 7. 강의를 들어야 하나


**CCNA 같은 정규 과정은 과하다.** 그건 스위치·라우터를 직접 설정하는 네트워크 엔지니어용이고, 여기서 필요한 건 "장비가 어떻게 생겼고 데이터가 어디서 오나" 수준. 위 내용이 사실상 8할.


남은 것 중 실제로 도움 되는 것:

- **IP / 서브넷 / 게이트웨이** — 위 1번 정도면 충분. 서브넷 마스크 계산까지는 불필요
- **SNMP** — 장비에서 수치를 긁어오는 주된 방법. "물어보면 숫자를 돌려주는 규약" 정도
- **RAID / LUN / 볼륨** — 스토리지 화면 작업 시 계속 나옴
