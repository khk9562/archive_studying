> 네트워크 스위치 등록 폼에 있는 4개 프로토콜 토글(CLI/REST/gNMI/SNMP)이 각각 뭔지 공부한 내용.

# 1. 포괄 개념

- 상위 개념: **네트워크 관리 프로토콜 (Network Management Protocol)**
- 수집 관점 용어: **네트워크 텔레메트리 (Network Telemetry)**
- 수집 방식은 크게 두 축으로 나뉜다:

| 방식                   | 개념             | 해당 프로토콜                      |
| -------------------- | -------------- | ---------------------------- |
| **Pull (폴링)**        | 수집기가 주기적으로 물어봄 | SNMP Polling, CLI, REST      |
| **Push (텔레메트리/이벤트)** | 장비가 스스로 보냄     | gNMI 스트리밍, SNMP Trap, syslog |

- gNMI 쪽 최신 흐름은 **스트리밍 텔레메트리(Streaming Telemetry)** / **모델 기반 텔레메트리(Model-Driven Telemetry, MDT)** 라고 부른다.

# 2. 프로토콜별 정리


| 프로토콜     | 통신 방식                                                  | 주로 가져오는 것                              | 필요한 자격증명                                      |
| -------- | ------------------------------------------------------ | -------------------------------------- | --------------------------------------------- |
| **CLI**  | SSH 로그인 후 `show` 명령 실행 → 출력 파싱                         | 장비 구성·인벤토리 등 다른 프로토콜로 안 나오는 정보         | SSH 계정/비밀번호                                   |
| **REST** | 장비의 HTTP API (벤더A eAPI, 벤더C NX-API 류)             | CLI 와 비슷한 정보를 구조화된 JSON 으로             | 인증 헤더 (Basic/Bearer)                          |
| **gNMI** | gRPC 기반 표준 인터페이스(OpenConfig) — 구독하면 장비가 **스트리밍으로 밀어줌** | 고빈도 텔레메트리 (인터페이스 카운터를 초 단위로)           | gNMI 계정/비밀번호 + 포트 (벤더A 6030 / 벤더C 50051) |
| **SNMP** | 표준 관리 프로토콜. 폴링(주기 질의) + Trap(이벤트 즉시 통보)                | 표준 MIB 메트릭(포트 상태·트래픽), Trap 으로 링크다운 알람 | v1/v2c=community, v3=USM 계정                   |


거칠게 나누면:

- **CLI/REST** → "무엇이 달려 있고 어떻게 설정돼 있나" (저빈도, 상세)
- **gNMI/SNMP Polling** → "지금 상태가 어떤가" (주기적 메트릭)
- **SNMP Trap** → "방금 무슨 일이 터졌나" (이벤트)

서로 대체제가 아니라 **보완재**라서 4개를 동시에 켜는 구성도 유효하다 (CLI 로 구성 정보 + gNMI 로 고빈도 메트릭 + SNMP 로 표준 메트릭·Trap). 단 장비가 지원해야 함 — 예: 보안벤더P 는 CLI·SNMP 만 지원.


## SNMP Polling vs Trap


|    | SNMP Polling           | SNMP Trap             |
| -- | ---------------------- | --------------------- |
| 방향 | 수집기 → 장비에 주기 질의        | 장비 → 수집기로 이벤트 시 즉시 통보 |
| 용도 | 트래픽·포트 상태 등 정기 메트릭     | 링크 다운, 팬 고장 같은 **알람** |
| 한계 | 주기 사이의 이벤트는 다음 폴링까지 모름 | 장비가 보내줘야만 앎           |


# 3. gRPC 가 뭔가


Google 이 만든 원격 호출(RPC) 프레임워크. "다른 서버의 함수를 내 함수처럼 호출하게 해주는 통신 규약".


|        | REST             | gRPC                               |
| ------ | ---------------- | ---------------------------------- |
| 데이터 형식 | JSON (텍스트)       | **Protocol Buffers** (바이너리, 작고 빠름) |
| 전송     | HTTP/1.1 위주      | **HTTP/2** (한 연결로 다중 요청)           |
| 호출 모양  | `GET /devices/3` | `GetDevice(request)` — 함수 호출처럼     |
| 계약     | OpenAPI (선택)     | `.proto` 파일 (강제, 코드 자동 생성)         |
| 통신 패턴  | 요청 1 : 응답 1      | 요청-응답 + **스트리밍** (양방향 가능)          |


핵심 차별점 2가지:

1. **스트리밍** — 연결을 열어두고 서버가 데이터를 계속 밀어줄 수 있다. "1초마다 최신 메트릭 보내줘" 구독 한 번이면 끝.
2. **강한 계약** — `.proto` 에서 코드가 생성되므로 필드 불일치가 컴파일 단계에서 잡힘.
- **gNMI** = **g**RPC **N**etwork **M**anagement **I**nterface. gRPC 스트리밍을 네트워크 장비 텔레메트리에 표준화한 것.
- 벤더C gNMI 기본 포트 50051 은 gRPC 진영의 관례적 기본 포트.
- 프로젝트에서는 SDN 클러스터(벤더A CloudVision) 수집도 CVP gRPC API 를 쓴다 — SDN 등록 폼의 Authorization JWT 가 이 호출의 인증 토큰.

# 4. "REST 놔두고 왜 이것들을 쓰나?" — 실시간성은 절반만 정답

- **gNMI, SNMP Trap → 실시간성 맞음.** REST 는 물어봐야 답이 오는 구조라 초 단위 카운터·즉시 장애 감지에 부적합.
- **SNMP Polling → 실시간성과 무관.** 진짜 이유는:
    1. **표준화·호환성** — REST API 는 벤더마다 제각각(eAPI, NX-API…)이고 아예 없는 장비도 많다. SNMP 는 30년간 모든 네트워크 장비가 지원한 **유일한 공통 언어**. 멀티벤더 수집기에는 사실상 필수.
    2. **경량성** — 수천 포트 카운터를 매주기 가져올 때 UDP 기반 SNMP 가 HTTP+JSON 보다 장비 부담이 훨씬 적다.
    3. **구형 장비 커버리지**.
- **CLI → 커버리지.** MIB/REST 로 노출 안 되는 상세 구성은 `show` 명령으로만 나온다.

한 줄 요약: **REST 를 안 쓰는 게 아니라, 프로토콜마다 잘하는 영역이 달라 병용한다.**
