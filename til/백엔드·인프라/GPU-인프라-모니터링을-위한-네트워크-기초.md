## 0. 왜 GPU 서버는 네트워크가 특별한가


일반 웹 서버는 **바깥의 사용자**와 통신한다. 트래픽이 건물 밖으로 나갔다 들어온다.


GPU 서버는 다르다. AI 학습은 **GPU 서버 수십~수백 대가 한 덩어리가 되어 하나의 작업**을 돌리고, 계산 한 스텝이 끝날 때마다 **모든 서버가 서로 결과를 주고받아 평균을 낸다**(All-Reduce).

1. **트래픽이 서버↔서버 사이에서 폭발한다.** 이것이 **east-west 트래픽**(건물 안 옆방끼리). 바깥과 오가는 north-south 보다 훨씬 크다
2. **가장 느린 한 대가 전체를 멈춘다.** 서로 결과를 기다려야 다음 스텝으로 가므로, 한 대의 포트 문제가 클러스터 전체 속도를 끌어내린다

> 💡 GPU 인프라 모니터링은 "평균이 괜찮은가"가 아니라 **"제일 나쁜 놈이 누구인가"**를 찾는 일에 가깝다.

## 1. 망이 4갈래로 갈린다


| 망            | 하는 일                          | 우리 코드의 서브유형             |
| ------------ | ----------------------------- | ----------------------- |
| 컴퓨트망(백엔드망)   | GPU ↔ GPU 결과 교환. 제일 빠르고 제일 비쌈 | SPINE / LEAF            |
| 스토리지망        | 학습 데이터를 스토리지에서 읽어옴            | GPU_STORAGE_LINK_SWITCH |
| 서비스망(프론트엔드망) | 사용자 요청, 잡 제출                  | —                       |
| 관리망          | BMC, 모니터링 수집, SSH             | GPU_MGMT_SWITCH         |


GPU 클러스터에서는 **스위치도 역할별로 종류가 나뉘고, 그걸 구분해서 보여줘야** 하기 때문에 제품에 저 서브유형들이 존재한다.

## 2. Leaf-Spine — SPINE / LEAF / BORDER_LEAF 의 정체


**옛날 3계층 방식**은 피라미드라서 아래→위→아래로 돌아갔고, 서버 쌍마다 **거리가 제각각**(2홉, 6홉)이었다. 모두가 서로 대화하는 GPU 워크로드에는 최악.


**Leaf-Spine** 은 이걸 평평하게 만든다.


```plain text
[Spine1]   [Spine2]   [Spine3]      ← 척추. 서버가 안 붙음
   │ ╳  ╳     ╳  ╳     ╳  │        ← 모든 Leaf ↔ 모든 Spine 연결
[Leaf1]    [Leaf2]    [Leaf3]       ← 잎. 서버가 여기 붙음
 │  │       │  │       │  │
GPU GPU    GPU GPU    GPU GPU
```

- **Leaf(잎)** = 서버가 직접 꽂히는 스위치. 랙마다 하나씩 두는 게 보통이라 **ToR(Top of Rack)** 이라고도 함
- **Spine(척추)** = Leaf 끼리 이어주는 상위 스위치. **서버는 절대 안 꽂는다**
- 규칙: **모든 Leaf 는 모든 Spine 에 연결**, Leaf 끼리는 직접 연결하지 않음
- 결과: 어느 서버에서 어느 서버로 가든 **Leaf → Spine → Leaf, 항상 3홉**. 거리가 균일해 예측 가능하고, 경로가 Spine 개수만큼 있어 한 곳이 죽어도 우회된다. 용량이 모자라면 **Spine 을 추가**하면 전체 대역폭이 늘어난다(수평 확장)
- **BORDER_LEAF** = 클러스터에서 **바깥세상으로 나가는 출구** 역할의 Leaf. 외부망·방화벽·인터넷이 여기 붙는다. 건물로 치면 정문이 있는 층

> 💡 토폴로지 화면에서 Spine 을 위, Leaf 를 아래로 그리는 건 미관이 아니라 **실제 물리 구조가 그렇기 때문**이다.

## 3. InfiniBand vs RoCE — SAN 스위치 얘기의 재방문


GPU ↔ GPU 컴퓨트망은 일반 이더넷으로 부족해 둘 중 하나를 쓴다.


|       | InfiniBand (IB)    | RoCE (RDMA over Converged Ethernet) |
| ----- | ------------------ | ----------------------------------- |
| 정체    | 전용 규격의 별도 네트워크     | 일반 이더넷 위에서 같은 효과를 냄                 |
| IP 사용 | 안 씀 (자체 주소 체계 LID) | 씀                                   |
| 장비    | IB 전용 스위치·케이블      | 이더넷 스위치 (고급형)                       |
| 비유    | FC/SAN 과 똑같은 발상    | iSCSI 와 똑같은 발상                      |


> 🚨 SAN 스위치와 판박이다. **InfiniBand 스위치도 데이터는 IP 없이 흐르지만, 상태를 조회하려면 별도 이더넷 관리 포트에 관리망 IP 가 있어야 한다.** GPU 클러스터 설계 문서에서 IB 스위치 관리 IP 누락 여부를 같은 방식으로 확인할 것.

- **RDMA** = 상대 서버의 메모리를 CPU 를 거치지 않고 직접 읽고 쓰는 기술. CPU 를 안 깨우니 빠르고 지연이 낮다. IB 와 RoCE 둘 다 이걸 하려고 존재한다
- **수집 경로가 다르다**: 이더넷/RoCE 스위치는 SNMP 로 긁지만, **InfiniBand 는 SNMP 가 아니라 서브넷 매니저(NVIDIA UFM 등)** 를 통해 조회한다

## 4. Lossless — GPU 망에서만 나오는 개념


일반 인터넷은 **패킷이 좀 버려져도 괜찮다**는 전제(TCP 재전송)로 만들어졌다. RDMA 는 속도를 위해 그 안전장치를 걷어냈기 때문에 **패킷 하나가 버려지면 성능이 절벽처럼 떨어진다.** 그래서 GPU 망은 **패킷을 안 버리는(lossless) 네트워크**로 설계한다.

- **PFC (Priority Flow Control)** — 받는 쪽이 벅차면 버리는 대신 **"잠깐 멈춰"** 신호를 보내 세운다
- **ECN (Explicit Congestion Notification)** — 막히기 **전에** 미리 "속도 줄여" 표시를 찍어 보낸다

**모니터링 지표 설계에 직접 영향**을 준다. 일반 네트워크는 대역폭 사용률(%)이 주요 지표지만 GPU 망은:

- **PFC pause 프레임 카운터** — 늘어나면 어딘가 막혀 계속 멈춰 세우고 있다는 뜻
- **ECN 마킹 수 / 혼잡 카운터**
- **포트 에러·재전송·드롭** — lossless 인데 드롭이 났다면 심각

> 💡 사용률이 60% 인데 학습 속도가 반토막인 상황이 흔하고, 원인은 대개 여기 있다. **GPU 사용률과 네트워크 지표를 나란히 봐야 한다.**


---


## 5. NVLink 는 네트워크가 아니다 (혼동 주의)

- **NVLink** = **서버 한 대 안에서** GPU 8장끼리 직결하는 내부 배선. 메인보드 안의 일이라 스위치도 IP 도 없다
- **NVSwitch** = 그 서버 안에서 GPU 들을 이어주는 칩. **네트워크 스위치가 아니다**

```plain text
서버 안:   GPU ─ NVLink ─ GPU                      (내부 배선. 장치 목록에 안 나옴)
서버 밖:   서버 ─ NIC ─ Leaf ─ Spine ─ Leaf ─ 서버   (진짜 네트워크)
```


장비 목록·토폴로지에 그릴 것은 아래쪽. NVLink 는 그 서버의 **내부 상태 지표**(NVLink 에러 카운터 등)로 다루는 게 맞다.


---


## 6. GPU 서버는 IP 를 아주 많이 갖는다


전형적인 8-GPU 서버 한 대:


| 인터페이스       | 개수              | 붙는 망  |
| ----------- | --------------- | ----- |
| 컴퓨트용 고속 NIC | 8개 (GPU 1장당 1개) | 컴퓨트망  |
| 스토리지용 NIC   | 2개              | 스토리지망 |
| 서비스용 NIC    | 2개              | 서비스망  |
| BMC 포트      | 1개              | 관리망   |


**서버 한 대에 IP 가 13개.** GPU 1장에 NIC 1개를 짝지어 붙이는 설계를 **rail-optimized(레일 최적화)** 라고 한다. GPU 가 자기 짝 NIC 로만 나가게 해 서버 내부 병목을 없애는 것.


> ⚠️ **제품 UI 에 영향**: 장치 상세에서 "IP 주소"를 한 칸으로 보여주면 GPU 서버는 표현이 안 된다. **인터페이스 목록 + 소속 망 라벨**로 보여줘야 의미가 있다.

## 7. 전력과 발열 — 세트로 따라오는 것


일반 서버 랙이 랙당 5~10kW 인데 **GPU 랙은 40~130kW**. 한 자릿수가 다르다. 그래서 다음이 1급 모니터링 대상이 된다.

- **랙 단위 소비 전력** — 랙 전원 용량 초과 여부
- **GPU 온도 / 전력 제한(power capping)** — 뜨거우면 GPU 가 스스로 속도를 낮춘다(**thermal throttling**). 성능 저하의 흔한 원인
- **수랭(liquid cooling)** — 고밀도 GPU 랙은 공랭이 안 돼 물을 쓴다. 냉각수 온도·유량·누수 감지가 감시 대상

이 데이터는 대부분 **BMC(Redfish)** 와 랙 PDU 에서 온다.

## 8. GPU 자체 지표는 어디서 오나


| 경로                | 성격          | 얻는 것                                |
| ----------------- | ----------- | ----------------------------------- |
| BMC / Redfish     | OS 밖 (하드웨어) | GPU 장착 여부, 온도, 전력, 하드웨어 장애          |
| DCGM / nvidia-smi | OS 안 (에이전트) | GPU 사용률, 메모리 사용량, ECC 에러, NVLink 상태 |


`nvidia-smi` 는 GPU 상태를 찍어주는 명령어, **DCGM** 은 그걸 서버로 계속 내보내주는 NVIDIA 공식 수집 도구. 에이전트 경로는 OS 가 살아 있어야 하고, 죽었을 때의 상태는 BMC 로 본다.

## 정리 — 기초 위에 얹을 다섯 가지

1. **east-west 트래픽** — 서버끼리의 통신이 주인공
2. **Leaf-Spine** — 그래서 나온 평평한 구조. SPINE / LEAF / BORDER_LEAF 의 정체
3. **InfiniBand / RoCE / RDMA** — 컴퓨트망의 특수 규격. IB 는 FC 처럼 IP 를 안 써서 **관리 IP 가 따로 필요**
4. **Lossless (PFC/ECN)** — 사용률보다 **혼잡·pause·드롭 카운터**가 중요한 이유
5. **NVLink 는 서버 내부** — 네트워크와 혼동 금지
